# DECOR — единый контекст проекта

**Версия:** 1.1  
**Дата фиксации:** 19 сентября 2026  
**Назначение:** единый source of truth для бизнес-стратегии, продукта, UX и технического развития сайта `decor-site`.

---

## 1. Суть проекта

DECOR — не просто интернет-магазин декоративных материалов.

Рабочая модель проекта:

> **Помогаем человеку решить задачу с интерьером и подобрать конкретные материалы для реализации этого решения.**

Каталог остаётся важнейшей частью проекта, но сайт должен работать в двух режимах:

1. Клиент знает, что ему нужно → идёт в каталог.
2. Клиент знает, чего хочет добиться, но не знает, какой материал выбрать → описывает задачу и получает помощь с подбором.

В перспективе DECOR развивается в сторону системы:

**задача клиента → подбор решения → визуализация → конкретные материалы → расчёт → поставка.**

---

## 2. Ключевое позиционирование

Главная стратегическая идея:

> **Не продавать человеку отделочный материал. Помогать ему решить задачу с интерьером — и продавать ему материалы, из которых это решение можно реализовать.**

Дополнительная формулировка для развития продукта:

> **Помогаем подобрать материалы для интерьера, показать результат и организовать поставку.**

## 3. Целевой пользовательский сценарий

### Сценарий A — человек знает товар

```text
Зашёл на сайт
→ Каталог
→ Категория / производитель
→ Товар
→ Вариант
→ Характеристики / изображения
→ Заявка или заказ
```

### Сценарий B — человек не знает товар

```text
Зашёл на сайт
→ «Не знаете, что выбрать?»
→ Описывает задачу
→ Прикладывает фото / размеры / план
→ Указывает бюджет и контакты
→ Получает подбор
→ Получает расчёт
→ Заказывает материалы
```

### Сценарий C — есть проект

```text
Проект / ТЗ / план / визуализация
→ Отправка проекта
→ Подбор материалов
→ Расчёт количества
→ Коммерческое предложение
→ Поставка
```

Эти сценарии должны существовать внутри одного сайта и одной системы обработки заявок.

## 4. Роль сайта

Сайт должен одновременно выполнять четыре функции:

### Каталог
Показывать реальные материалы, производителей, варианты и характеристики.

### Консультант
Помогать человеку, который не знает точного товара.

### Вход для профессионалов
Принимать проекты, ТЗ и запросы от дизайнеров, архитекторов, строителей и бизнеса.

### Основа будущего AI-сервиса
Позволить в перспективе перейти от ручного подбора к автоматическому анализу задачи, визуализации и комплектации.

## 5. Hero — текущая стратегическая концепция

Существующий брендовый заголовок сохраняется:

> **Детали, которые создают пространство**

Текущий смысловой блок hero должен развиваться так:

**Eyebrow**

`АРХИТЕКТУРНЫЙ ДЕКОР`

**H1**

`Детали, которые создают пространство`

**Описание**

`Декоративные панели, молдинги, плинтусы, каменный шпон и другие материалы для современных интерьеров.`

**CTA-блок**

> **Не знаете, что выбрать?**

`Опишите задачу — мы поможем подобрать материалы под ваш интерьер, бюджет и задачу.`

**Основная кнопка**

`Помочь с подбором`

**Вторичная кнопка**

`Смотреть каталог`

### Принцип

В hero не нужно заставлять человека сначала определить категорию товара.

Первый вопрос должен быть не:

> «Что вы хотите купить?»

а:

> **«Что вы хотите сделать?»**

## 6. Архитектура формы

Не создавать отдельную изолированную систему формы для hero.

Нужен единый механизм заявок.

### Сейчас

```ts
{
  name,
  phone,
  product,
  website
}
```

### Целевая базовая структура

```ts
{
  name,
  phone,
  product,
  message,
  website
}
```

Где:

- `product` — конкретный товар, если пользователь пришёл со страницы товара;
- `message` — описание задачи;
- `website` — honeypot-антиспам.

### В будущем можно расширить

```ts
{
  name,
  phone,
  product,
  message,
  city,
  budget,
  projectFiles,
  source,
  website
}
```

Сама форма не должна знать, что дальше происходит с заявкой.

Целевая архитектура:

```text
Hero / Product / Project
        ↓
      Request
        ↓
       API
        ↓
  обработчик заявки
        ↓
 ┌──────┴─────────┐
 │                │
Telegram       AI pipeline
(сейчас)        (позже)
```

Это позволяет заменить ручную обработку на AI-процесс без переделки hero.

## 7. B2C и B2B

Один сайт обслуживает разные типы клиентов.

### B2C

Клиент может прийти с запросом:

- нужен плинтус;
- нужна акцентная стена;
- нужно оформить ТВ-зону;
- хочется современный интерьер;
- не знаю, какой материал выбрать;
- нужен вариант под конкретный бюджет.

### Дизайнер / архитектор

Предлагаем:

- подбор материалов;
- образцы;
- визуализацию;
- спецификацию;
- расчёт;
- поставку.

### Строитель / ремонтная компания

Предлагаем:

- работу по ТЗ;
- расчёт количества;
- коммерческое предложение;
- цену;
- сроки;
- поставку.

### Застройщик / бизнес

Предлагаем:

- проектные объёмы;
- комплектацию;
- КП;
- стабильные поставки.

## 8. Стартовая бизнес-модель

Запускать модель постепенно, без требования сразу построить сложную платформу.

### Первый этап

Каталог + заявки + ручной подбор + продажи.

### Второй этап

Каталог + реальные кейсы + контент + визуализация + подбор.

### Третий этап

AI-подбор + AI-визуализация + привязка к конкретным товарам каталога.

### Четвёртый этап

3D-конфигуратор + спецификация + автоматический расчёт.

### Пятый этап

Полный AI-сценарий:

**фото → задача → дизайн → материалы → спецификация → стоимость → заказ.**

## 10. Разница между AI-визуализацией и настоящим 3D

Не смешивать два разных продукта.

### AI-визуализация

Используется для быстрого показа идеи на фотографии клиента.

Сильная сторона — скорость и выразительность.

Ограничение — AI нельзя считать источником точной геометрии, размеров, цвета и технических свойств товара.

### Настоящий 3D

Сцена содержит реальные объекты:

```text
стена
+
3D-модель D317
+
3D-модель D001
+
материалы
+
масштаб
+
раскладка
```

Это даёт возможность:

- менять размер;
- менять расположение;
- менять комбинации;
- рассчитывать количество;
- формировать спецификацию.

Целевая система должна использовать оба подхода, а не выбирать только один.

## 11. Подготовка каталога к AI

Текущий каталог уже построен так, чтобы стать основой будущего AI-подбора.

### Основные сущности

```text
Product
 ├── Variant
 └── ProductImage
```

### Product

Товар/модель.

### Variant

Конкретное исполнение:

- артикул;
- цвет;
- размер;
- публикация.

### ProductImage

Типы изображений:

- `catalog`
- `interior`
- `detail`
- `texture`
- `installation`

И метаданные:

- источник;
- статус;
- локальный путь;
- связь с вариантом;
- primary/sort order;
- provenance.

## 13. Изображения — правила проекта

Ключевой принцип:

> **AI не должен подменять реальный товар красивой, но недостоверной версией.**

Для каталога:

- реальный товар сохраняется;
- изображения должны быть локальными;
- внешние URL не используются runtime-сайтом;
- `sourceUrl` может храниться только как provenance/аудит;
- AI может помогать создавать интерьерную сцену, но продукт должен оставаться привязанным к референсу.

### Pipeline

```text
supplier source
→ local source archive
→ processing / upscale
→ public local asset
→ productImages metadata
→ site
```

## 15. Изображения: runtime и source

Нужно сохранять правило:

**runtime = только локальные assets.**

То есть приложение не должно зависеть от:

- CloudFront URL;
- сайтов производителей;
- сайтов дилеров;
- внешних CDN.

Внешние страницы/URL допустимы только как источник для ручного или автоматизированного импорта.

```text

→ расчёт
→ продажа
→ валовая прибыль
```

Отдельно учитывать:

- B2C;

- строителей;

Полезно фиксировать причину отказа:

- дорого;

- не удалось связаться.

## 15. B2B — полноценный сценарий внутри единого сайта

DECOR одновременно обслуживает B2C и B2B-клиентов. Отдельный B2B-сайт не является частью концепции.

### Вход для профессионалов

> **Принимать проекты, ТЗ и запросы от дизайнеров, архитекторов, строителей и бизнеса.**

Профессиональный клиент должен использовать DECOR как рабочую точку входа для проекта, а не только как каталог.

### Что должен закрывать сайт для B2B

**Проект / ТЗ / запрос → подбор материалов → расчёт → коммерческое предложение → согласование → заказ → поставка.**

Клиент должен иметь возможность решать эти задачи непосредственно через DECOR. Телефон, Telegram и другие каналы являются дополнительными способами коммуникации с менеджером, а не обязательным выходом с сайта.

### Почему профессионал будет работать с DECOR

У дизайнеров и других профессиональных клиентов уже могут быть привычные поставщики и индивидуальные условия. Поэтому DECOR не строит B2B-модель только вокруг идеи замены текущего поставщика.

Ценность DECOR для профессионала строится на сочетании:

- персональных условий сотрудничества;
- ведения и защиты проекта;
- быстрого подбора материалов;
- расчёта количества;
- подготовки коммерческого предложения;
- образцов и технических материалов;
- визуализации;
- экономии времени на комплектацию;
- организованной поставки.

### Основные B2B-сценарии

**Знаю, что нужно**
→ каталог → товар → вариант → количество → запрос расчёта.

**Есть задача, но нет готовой спецификации**
→ проект / описание → подбор → расчёт → КП.

**Есть ТЗ / спецификация**
→ загрузка документов → сопоставление с ассортиментом → варианты / аналоги → расчёт → КП.

**Есть большой проект**
→ передача проекта → комплектация → спецификация → КП → согласование → заказ → поставка.

### Проектный контур

В перспективе у профессионального клиента должен быть рабочий контур:

**Проект → материалы → варианты → количества → персональные цены → документы → визуализации → спецификация → КП → статус заказа → поставка.**

### Будущая AI/3D-модель для B2B

**проект / ТЗ → анализ → поиск товаров в каталоге DECOR → подбор → AI/3D-визуализация → спецификация → расчёт → КП.**

### Архитектурный принцип

Нынешний универсальный входящий запрос должен со временем поддерживать:

```ts
{
  type,
  clientType,
  name,
  phone,
  company,
  projectName,
  message,
  files,
  products,
  quantity,
  budget,
  city,
  deadline
}
```

Сейчас обработка может оставаться простой и передавать запрос менеджеру. В дальнейшем этот же объект должен превращаться в проект и запускать автоматический pipeline.

### Ключевой принцип

> **Один DECOR для B2C и B2B, но с разными сценариями работы.**

B2C: **«Не знаете, что выбрать?»**

B2B: **«Есть проект или ТЗ?»**

---

## 16. Текущая точка старта

Следующий этап реализации сайта:

1. Hero главной страницы должен вести в два основных сценария: **«Помочь с подбором»** и **«Передать проект / ТЗ»**.
2. `RequestForm` и `/api/request` должны стать универсальным механизмом входящих обращений.
3. Каталог, товары, варианты и изображения остаются единой базой для B2C и B2B.
4. Нельзя ломать текущую систему локальных runtime-изображений и каталогов.
5. Структуру данных нужно развивать так, чтобы без переписывания сайта добавить AI-подбор, AI/3D-визуализацию, проектный кабинет, спецификацию и КП.

## 17. Граница текущего MVP

На первом запуске AI и полноценный 3D-конфигуратор не являются обязательными.

MVP:

**каталог + помощь с подбором + вход для профессионалов + приём проектов/ТЗ + ручной подбор + расчёт + продажа.**

AI/3D добавляются поверх уже работающего коммерческого процесса, а не вместо него.

## DECOR PRO — интерфейс для профессионалов

### Принцип

DECOR является единым сайтом для B2C и B2B. Для профессиональных клиентов предусмотрен отдельный рабочий режим **DECOR PRO**, а не отдельный сайт.

Публичная часть сайта остаётся простой: каталог, подбор и общая информация.

После входа профессионалу открывается рабочий интерфейс, ориентированный на ведение проектов.

### Вход в DECOR PRO

На публичном сайте основной CTA для профессионального сегмента:

**Для профессионалов**

Внутри:

- вход существующего профессионального клиента;
- регистрация / заявка на подключение к DECOR PRO.

Не требуется делать отдельный B2B-сайт.

### Рабочее пространство профессионала

DECOR PRO должен помогать профессионалу выполнять рабочие задачи непосредственно внутри сайта:

**проекты → материалы → варианты → количества → персональные условия → спецификация → КП → документы → заказы → поставка**

Пример структуры:

- Мои проекты
- В работе
- Расчёты
- Коммерческие предложения
- Заказы
- Каталог
- Образцы
- Документы

### Проект

Каждый проект связан с конкретным профессиональным клиентом.

В проекте могут храниться:

- название и объект;
- проект / ТЗ / спецификация;
- выбранные товары;
- варианты товаров;
- количества;
- персональные цены и условия;
- визуализации;
- документы;
- коммерческие предложения;
- статусы согласования;
- статус заказа и поставки.

### Почему DECOR PRO нужен профессионалу

Не предполагается, что дизайнер или другой профессионал должен отказаться от всех существующих поставщиков.

DECOR PRO должен становиться дополнительным и затем постоянным рабочим инструментом за счёт:

- персональных условий;
- проектной работы;
- быстрого поиска и подбора;
- расчёта;
- комплектации;
- подготовки КП;
- визуализации;
- экономии времени;
- удобного ведения проектов.

### Будущее развитие

DECOR PRO является основой для будущего AI/3D-контура:

**проект / ТЗ → AI-анализ → товары из каталога → подбор → AI/3D-визуализация → спецификация → расчёт → КП → заказ**

### Архитектурный принцип

Публичный DECOR и DECOR PRO используют один каталог, одни товары, варианты и изображения.

Различается прежде всего пользовательский интерфейс и сценарий работы.

```text
DECOR
├── Публичная часть
│   ├── Каталог
│   ├── Подбор
│   └── Информация
│
└── DECOR PRO
    ├── Проекты
    ├── Подбор и комплектация
    ├── Персональные условия
    ├── Спецификации
    ├── КП
    ├── Документы
    ├── Заказы
    └── AI / 3D
```
