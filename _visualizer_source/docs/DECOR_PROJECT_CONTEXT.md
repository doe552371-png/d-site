# DECOR — единый контекст проекта

**Версия:** 1.0  
**Дата фиксации:** 18 сентября 2026  
**Назначение:** единый source of truth для бизнес-стратегии, продукта, UX и технического развития сайта `decor-site`.

---

## 1. Суть проекта

DECOR — не просто интернет-магазин декоративных материалов.

Рабочая модель проекта:

> **Помогаем человеку решить задачу с интерьером и подобрать конкретные материалы для реализации этого решения.**

Каталог остаётся важнейшей частью проекта, но сайт должен работать в двух режимах:

1. Клиент знает, что ему нужно → идёт в каталог.
2. Клиент знает, чего хочет добиться, но не знает, какой материал выбрать → описывает задачу и получает помощь с подбором.

В перспективе DECOR развивается в сторону системы:

**задача клиента → подбор решения → визуализация → конкретные материалы → расчёт → поставка.**

---

## 2. Ключевое позиционирование

Главная стратегическая идея:

> **Не продавать человеку отделочный материал. Помогать ему решить задачу с интерьером — и продавать ему материалы, из которых это решение можно реализовать.**

Дополнительная формулировка для развития продукта:

> **Помогаем подобрать материалы для интерьера, показать результат и организовать поставку.**

---

## 3. Целевой пользовательский сценарий

### Сценарий A — человек знает товар

```text
Зашёл на сайт
→ Каталог
→ Категория / производитель
→ Товар
→ Вариант
→ Характеристики / изображения
→ Заявка или заказ
```

### Сценарий B — человек не знает товар

```text
Зашёл на сайт
→ «Не знаете, что выбрать?»
→ Описывает задачу
→ Прикладывает фото / размеры / план
→ Указывает бюджет и контакты
→ Получает подбор
→ Получает расчёт
→ Заказывает материалы
```

### Сценарий C — есть проект

```text
Проект / ТЗ / план / визуализация
→ Отправка проекта
→ Подбор материалов
→ Расчёт количества
→ Коммерческое предложение
→ Поставка
```

Эти сценарии должны существовать внутри одного сайта и одной системы обработки заявок.

---

## 4. Роль сайта

Сайт должен одновременно выполнять четыре функции:

### Каталог
Показывать реальные материалы, производителей, варианты и характеристики.

### Консультант
Помогать человеку, который не знает точного товара.

### Вход для профессионалов
Принимать проекты, ТЗ и запросы от дизайнеров, архитекторов, строителей и бизнеса.

### Основа будущего AI-сервиса
Позволить в перспективе перейти от ручного подбора к автоматическому анализу задачи, визуализации и комплектации.

## 5. Hero — текущая стратегическая концепция

Существующий брендовый заголовок сохраняется:

> **Детали, которые создают пространство**

Текущий смысловой блок hero должен развиваться так:

**Eyebrow**

`АРХИТЕКТУРНЫЙ ДЕКОР`

**H1**

`Детали, которые создают пространство`

**Описание**

`Декоративные панели, молдинги, плинтусы, каменный шпон и другие материалы для современных интерьеров.`

**CTA-блок**

> **Не знаете, что выбрать?**

`Опишите задачу — мы поможем подобрать материалы под ваш интерьер, бюджет и задачу.`

**Основная кнопка**

`Помочь с подбором`

**Вторичная кнопка**

`Смотреть каталог`

### Принцип

В hero не нужно заставлять человека сначала определить категорию товара.

Первый вопрос должен быть не:

> «Что вы хотите купить?»

а:

> **«Что вы хотите сделать?»**

## 6. Архитектура формы

Не создавать отдельную изолированную систему формы для hero.

Нужен единый механизм заявок.

### Сейчас

```ts
{
  name,
  phone,
  product,
  website
}
```

### Целевая базовая структура

```ts
{
  name,
  phone,
  product,
  message,
  website
}
```

Где:

- `product` — конкретный товар, если пользователь пришёл со страницы товара;
- `message` — описание задачи;
- `website` — honeypot-антиспам.

### В будущем можно расширить

```ts
{
  name,
  phone,
  product,
  message,
  city,
  budget,
  projectFiles,
  source,
  website
}
```

Сама форма не должна знать, что дальше происходит с заявкой.

Целевая архитектура:

```text
Hero / Product / Project
        ↓
      Request
        ↓
       API
        ↓
  обработчик заявки
        ↓
 ┌──────┴─────────┐
 │                │
Telegram       AI pipeline
(сейчас)        (позже)
```

Это позволяет заменить ручную обработку на AI-процесс без переделки hero.

## 7. B2C и B2B

Один сайт обслуживает разные типы клиентов.

### B2C

Клиент может прийти с запросом:

- нужен плинтус;
- нужна акцентная стена;
- нужно оформить ТВ-зону;
- хочется современный интерьер;
- не знаю, какой материал выбрать;
- нужен вариант под конкретный бюджет.

### Дизайнер / архитектор

Предлагаем:

- подбор материалов;
- образцы;
- визуализацию;
- спецификацию;
- расчёт;
- поставку.

### Строитель / ремонтная компания

Предлагаем:

- работу по ТЗ;
- расчёт количества;
- коммерческое предложение;
- цену;
- сроки;
- поставку.

### Застройщик / бизнес

Предлагаем:

- проектные объёмы;
- комплектацию;
- КП;
- стабильные поставки.

## 8. Стартовая бизнес-модель

Запускать модель постепенно, без требования сразу построить сложную платформу.

### Первый этап

Каталог + заявки + ручной подбор + продажи.

### Второй этап

Каталог + реальные кейсы + контент + визуализация + подбор.

### Третий этап

AI-подбор + AI-визуализация + привязка к конкретным товарам каталога.

### Четвёртый этап

3D-конфигуратор + спецификация + автоматический расчёт.

### Пятый этап

Полный AI-сценарий:

**фото → задача → дизайн → материалы → спецификация → стоимость → заказ.**

## 9. AI + 3D — целевая модель

Это стратегическое направление, но не обязательная часть первого запуска.

### Целевая цепочка

```text

+

+

+
бюджет

        ↓

        ↓

```

## 10. Разница между AI-визуализацией и настоящим 3D

Не смешивать два разных продукта.

### AI-визуализация

Используется для быстрого показа идеи на фотографии клиента.

Сильная сторона — скорость и выразительность.

Ограничение — AI нельзя считать источником точной геометрии, размеров, цвета и технических свойств товара.

### Настоящий 3D

Сцена содержит реальные объекты:

```text
стена
+
3D-модель D317
+
3D-модель D001
+
материалы
+
масштаб
+
раскладка
```

Это даёт возможность:

- менять размер;
- менять расположение;
- менять комбинации;
- рассчитывать количество;
- формировать спецификацию.

Целевая система должна использовать оба подхода, а не выбирать только один.

## 11. Подготовка каталога к AI

Текущий каталог уже построен так, чтобы стать основой будущего AI-подбора.

### Основные сущности

```text
Product
 ├── Variant
 └── ProductImage
```

### Product

Товар/модель.

### Variant

Конкретное исполнение:

- артикул;
- цвет;
- размер;
- публикация.

### ProductImage

Типы изображений:

- `catalog`
- `interior`
- `detail`
- `texture`
- `installation`

И метаданные:

- источник;
- статус;
- локальный путь;
- связь с вариантом;
- primary/sort order;
- provenance.

## 12. Будущие AI-метаданные товара

По мере накопления опыта можно расширять товарные данные.

Пример:

```ts
{
  applicationTags: [
    "tv-zone",
    "accent-wall",
    "bedroom"
  ],
  styleTags: [
    "modern",
    "minimal",
    "classic"
  ],
  colorTags: [
    "white",
    "natural"
  ],
  budgetLevel: "medium",

    "..."
  ]
```

Эти поля не нужно придумывать массово заранее. Их лучше формировать постепенно на основе реальных запросов клиентов, ассортимента и опыта ручного подбора.

## 13. Изображения — правила проекта

Ключевой принцип:

> **AI не должен подменять реальный товар красивой, но недостоверной версией.**

Для каталога:

- реальный товар сохраняется;
- изображения должны быть локальными;
- внешние URL не используются runtime-сайтом;
- `sourceUrl` может храниться только как provenance/аудит;
- AI может помогать создавать интерьерную сцену, но продукт должен оставаться привязанным к референсу.

### Pipeline

```text
supplier source
→ local source archive
→ processing / upscale
→ public local asset
→ productImages metadata
→ site
```

## 15. Изображения: runtime и source

Нужно сохранять правило:

**runtime = только локальные assets.**

То есть приложение не должно зависеть от:

- CloudFront URL;
- сайтов производителей;
- сайтов дилеров;
- внешних CDN.

Внешние страницы/URL допустимы только как источник для ручного или автоматизированного импорта.

## 16. MVP первого этапа

Цель первого этапа — не построить весь AI-продукт.

Цель:

> **получить реальные обращения, реальные подборы, первые продажи и данные для последующей автоматизации.**

### Уже сейчас важны

1. Каталог.
2. Хорошие карточки товаров.
3. Локальные изображения.
4. Форма «Помочь с подбором».
5. Форма «Есть проект?».
6. Telegram как канал обработки заявки.
7. Учёт всех обращений.
8. Первые реальные визуальные кейсы.

---

## 17. Что сознательно НЕ делаем на первом этапе

- не строим собственного AI-агента;
- не делаем сложный 3D-конфигуратор;
- не пытаемся загрузить весь мировой ассортимент;
- не строим отдельный B2B-сайт;
- не делаем огромную CRM;
- не подключаем внешние изображения в runtime;
- не считаем AI-визуализацию источником технической истины.

## 18. Как измеряем бизнес

Базовая воронка:

```text
трафик
→ обращение
→ контакт состоялся
→ подбор
→ расчёт
→ продажа
→ валовая прибыль
```

Отдельно учитывать:

- B2C;
- дизайнеров;
- строителей;
- B2B.

Полезно фиксировать причину отказа:

- дорого;
- передумал;
- выбрал другой материал;
- нет в наличии;
- не устроили сроки;
- не устроила доставка;
- просто интересовался;
- не удалось связаться.

## 19. Важная продуктовая гипотеза

Для проекта принципиально важно проверить:

> **Увеличивает ли визуализация вероятность покупки материалов?**

Также нужно проверить:

> **Готов ли человек обращаться за подбором, не зная названия конкретного товара?**

Если эти гипотезы подтверждаются реальными заявками, инвестиции в AI/3D становятся обоснованнее.

## 23. Контрольное определение проекта

Если нужно одним абзацем объяснить, что такое DECOR:

> **DECOR — каталог интерьерных материалов и система подбора решений для интерьера. Клиент может выбрать конкретный товар самостоятельно или описать свою задачу, а дальше получить помощь с подбором, визуализацией, расчётом и поставкой. В перспективе эта система должна перейти к AI-подбору и 3D-визуализации с использованием конкретных товаров из каталога.**

---

## 24. Главное решение, зафиксированное на этой версии

Мы не строим «просто каталог».

Мы строим **каталог как фундамент будущего сервиса подбора и комплектации интерьера**.

Hero, формы, данные товаров, изображения и API должны развиваться именно в эту сторону.
